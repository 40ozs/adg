## 2. What an alert is, in six sentences

An alert says: *this trigger fired about this thing, and here is what happened.* Its identity
is a SHA-256 of the trigger, the subject and a discriminator — **never of the content**, which
is what lets the same condition in the same place be the same alert next week rather than a new
one every time. It carries **no severity of its own**: it carries the grading of whatever
produced it, because a third severity vocabulary beside `Severity` and `ChangeSeverity` would be
a third thing to keep in step and the first drift would have an alert grading an exposure
differently from the finding it was raised about. A **suppressed occurrence is still written
down**, so "we were not told" and "it did not happen" stay separable afterwards. A **resolution
and a reopen are never suppressed**, because the failure mode of an alerting system is not
"too loud" but "somebody believed the last thing it said". And **raising an alert is durable
before anything tries to deliver it**, so a webhook that is down can never roll back the
ingestion that produced it.

Full treatment: [`docs/architecture/alerting.md`](../architecture/alerting.md).
Operator reference: [`docs/operations/alerting.md`](../operations/alerting.md).

## 4. Design decisions worth knowing

### An alert carries no severity of its own

It names its trigger and carries the source's own grading in its payload. Two severity scales
already exist and they do not mean the same thing — one describes a consequence in the estate,
the other how much an edit moved — so averaging them would produce a number with no unit, and
keeping a third in step would be a drift waiting to happen.

### Two lifecycles, enforced in the database

A risk finding is a **condition** that can resolve and come back. An ACL edit is an **event**
that cannot un-happen. `ck_alerts_transient_never_resolves` makes the distinction an invariant.
Without it, a resolution pass could close an ACL change and make the feed look tidier than the
estate is — and the interface would show a "Resolved" badge inviting somebody to believe the
edit had been reverted.

### The cooldown is measured from the last **notification**

Not from the last occurrence. Measured from the last occurrence, something changing every
minute inside a fifteen-minute cooldown would push the eligible instant out on every pass and
the alert would never be delivered at all — the storm control would have become a silencer.
Pinned by `test_the_window_is_measured_from_the_last_notification_not_the_last_occurrence`.

### A reopen is checked before the payload digest

A reopen's content is frequently *identical* to the original's — the same finding, the same
evidence. Comparing digests first would call it a duplicate, and an exposure that came back
would have been announced once, months earlier.

### `delivered_digest` moves only on a notification

A suppressed repeat updates the counts and leaves it alone. If a suppression moved it, the next
occurrence of the content an operator was actually shown would compare unequal and read as new —
the deduplication inverted, quietly, in the direction that produces noise about things nobody
was told. Pinned by `test_a_suppression_does_not_move_the_delivered_digest`.

### The outbox has no `deliver` and no `delete`

No `deliver`, so a storage bug cannot become a delivery bug and `InMemoryOutbox` is a complete
substitute in every dispatch test. No `delete`, because a delivered row is the evidence it was
delivered and an abandoned one the evidence it was not.

### Retryability is written out, not inferred from a range

A permanent failure treated as retryable keeps a delivery that will never succeed at the front
of the queue; a transient one treated as permanent abandons a real alert because a proxy
hiccuped. So 408/425/429 and every 5xx are retryable, **3xx is permanent** (following a
redirect would deliver an estate's exposure report to a host nobody configured), and every
other 4xx is the sender's fault.

### No jitter in the retry schedule

Jitter spreads a thundering herd across many senders and there is one sender here. What it
would buy is unpredictability in a test suite, which is the one thing a delivery schedule must
not have.

### The layering is a test, not a convention

`tests/alerts/test_layering.py` reads the import graph from the **source** and fails if
anything in `app/alerts` imports `app.risk_engine`, `app.changes`, a repository, a service,
SQLAlchemy or FastAPI — or if anything in `app/risk_engine` imports `app.alerts` or `httpx`.
Verified by mutation: adding `import sqlalchemy` to `app/alerts/dedupe.py` fails it.

The cost is three flat record types (`ChangeNotice`, `AccessExpansion`, `FindingNotice`) and one
conversion per source in `app/services/alerts.py`. It buys detection tests that need no database
fixtures and a vocabulary a reader can see by reading three dataclasses.

### The one duplication the layering costs, and how it is pinned

`app/alerts/configuration.py` writes out the five severity names rather than importing
`Severity`. `test_the_severity_vocabulary_matches_the_risk_engine` compares them to
`SEVERITY_ORDER` in rank order, so adding a severity fails a test rather than producing a policy
file refused at startup in somebody's installation.

The same device covers the six enums written out in `app/models/schema.py` (their values appear
in check constraints, so they cannot import the module that imports them) and the frozen
vocabularies in the migration.

### A watch covers exactly what it names

A directory watch covers that directory, not its children. A share watch covers the share ACL
and the share record, not the directories beneath it. There is **no server watch**. A watch that
quietly meant "and everything below" would fire on a subtree the operator never named, and on a
large share it would fire constantly.

### A trigger a kind could never fire is refused, not saved

`TRIGGERS_BY_WATCH_KIND` is enforced in `Watch.__post_init__` and served by the API so a client
builds its form from the server's copy. A watch that accepted such a subscription would be
configured, listed in the interface, and silent forever — and silence from a monitoring feature
reads as "nothing happened".

### The post-completion hook is opt-in, and being off is never silent

`ADG_ALERTS_ON_RUN_COMPLETION` defaults to **false**. Turning it on adds an incremental
evaluation, a change-feed scan per watch and a delivery attempt to the collector's final
request, on an engine nobody has profiled against millions of ACEs (Phase 8A prerequisite 6).
Every completion logs a `post_run` line saying it was skipped, and the risk report says *"the
rules have never been evaluated"* rather than showing a clean empty report.

**This default was chosen for that reason, and it is also what keeps Phase 8A's suite honest.**
With the hook on, seeding through the ingestion endpoints opens findings before a test's own
`evaluate_estate` runs, and five of 8A's lifecycle tests fail on a premise that is no longer
true. Turning the hook off restored all 22 without touching one of them.

### Nothing downstream of ingestion can fail an ingestion

Three boundaries: enqueue in the alert's transaction; deliver in a separate pass;
and `app/api/scan_runs.py` wraps the hook in its own `try`/`except` for the failures
`evaluate_run_after_commit` cannot catch itself. Without that third one, a broken downstream
would turn a successful completion into a 500 *after* the commit, and the collector would retry
a run already recorded. Pinned by
`test_a_scan_run_completes_even_when_the_alert_pipeline_raises`, which replaces the hook with
one that raises outright and asserts the seeding still completes.

### The risk report renders its coverage whether or not it is reassuring

`has_ever_run`, `complete`, the skipped rules, and the truncation note — on every response and
in the banner above the counts, in all three states. A caveat that appears only when things are
bad teaches a reader to skip it, and the one time it matters they will.

### Severity counts include their zeros; status counts ignore the status filter

A facet list that omitted the empty severities would make a report with no critical findings
look like a report with no critical *category*. And the status counts are taken with the status
clause removed, so the default view can say "12 open, and 340 resolved are not shown" — without
which a default filter is indistinguishable from a complete result.

### The evidence drawer is a URL

`?finding=<key>` renders the records server-side. Linkable, which is what somebody wants when
pasting a finding into a ticket, and it carries the reader's page trail so opening the drawer on
page three does not return them to page one.

### `isEmpty` is deliberately never true on both new pages

`classify` interprets an empty list against *collector* coverage, which is the wrong question
here: it would print "ADG could not check whether collection has run" above a report whose own
coverage is stated exactly, two elements up. Both pages answer their own emptiness and use
`classify` only for the failure and session states.

### Two new capabilities, and why `alerts:manage` is admin-only

Reading an alert and deciding who gets woken up are different disclosures. Somebody who could
quietly disable the watch on the payroll share could make an exposure land in nobody's inbox —
this product's own failure mode, performed on the product. A **governance administrator
deliberately does not get it**: choosing who is paged is an operations decision, not part of
running an access review.

### The browser's writes are two declared route handlers, not a widened proxy

`/api/adg` forwards GET only, deliberately: every other write in ADG is collector ingestion,
which has no business coming through a browser session. Widening it to POST would have made the
browser a route into ingestion. `frontend/app/api/watches/` is the one write a person
legitimately makes from a page, so what the browser may write is reviewable by reading two files.

### Three defects the implementation found in itself, and how

Two were found by tests. **The third was found only by running the whole feature end to end
against a real database**, which is worth recording because the suite was green when it was
there.

* **One bad watch silenced the whole estate's alerting.** A watch whose key the change feed
  cannot scope on — a directory watch whose key is not a UNC path — raised out of the
  per-watch loop. That killed the detection pass, and because the failure returned early from
  `evaluate_run_after_commit`, it also skipped the **finding** half. So a single mistyped
  watch stopped every `critical_risk_finding_opened` alert in the estate — the one trigger
  that is supposed to fire whether or not anybody configured a watch correctly — and left
  nothing behind but a log line and a feed that looked quiet. Exactly the failure mode this
  phase is about, in this phase's own code.

  Three fixes, at three depths: the per-watch loop catches and records the watch as a
  coverage note rather than dying; the post-run pass attempts the finding half even when the
  change half failed, because they are independent; and `POST /alerts/watches` now **refuses**
  a key nothing can scope, so such a row is not created in the first place. Pinned by
  `TestOneBadWatchCannotSilenceTheEstate`, whose three tests cover all three.

  The creation check builds the scope **and exercises its predicates**: `ChangeScope`'s own
  validation refuses only an empty key, and the parse that rejects a malformed UNC path
  happens when the predicates are built. The first version of the check constructed the scope
  alone, accepted the bad key, and was caught by its own test.

* **`enqueue` reported `-1` rows written.** A multi-row `INSERT … ON CONFLICT DO NOTHING`
  goes through the driver's executemany path, where `rowcount` is `-1` and says nothing — so
  the idempotency count was meaningless and would have reported a duplicate enqueue as a
  successful one. Now `RETURNING` the ids and counting them. Caught by the PostgreSQL test,
  not by review.
* **`SubjectView` collided with the change feed's**, which makes FastAPI qualify *both* names
  in the published document — silently renaming another phase's schema. Caught by the
  frontend's contract check, which is exactly the failure that test exists for.

key* and is not what the change feed selects on. The first draft of
`docs/operations/alerting.md` and the API's own field description both named the prefixed
form, which the creation check refuses. Corrected in both, and
`tests/alerts/test_watch_keys.py` now pins every accepted and refused shape so the prose
cannot drift from the check again.

## 7. Known limitations

1. **No acknowledgment, snooze or risk acceptance.** Phase 8A's limitation 7, unchanged. It is
   a person's decision *about* an alert or a finding, and putting it on the row would let the
   next pass overwrite somebody's judgment.
2. **No email, Slack, Teams or PagerDuty sink.** The abstraction is complete and two sinks
   exercise every part of it. Writing a vendor integration speculatively would put a message
   format in the repository with nobody to say whether it is the right one.
3. **A watch covers what it names, not a subtree.** Watching a large share's contents means a
   watch per directory. What a subtree watch has to settle first is what it does on a share
   with a hundred thousand directories.
4. **The expansion trigger is bounded** at 25 effective-access resolutions per pass and the
   change feed at 200 changes per watch. Both are reported on the evaluation rather than
   hidden, and both mean the alerts beyond them wait for the next pass.
5. **`AlertService.evaluate_window` uses the run's window, not a watermark.** Overlapping
   windows are re-read and deduplicated, which is the safe direction — but a window that never
   overlaps far enough back could miss a change nothing re-reads. A stored watermark per watch
   would settle it.
6. **Nothing prunes alerts, events or deliveries.** They inherit the retention question
   `object_versions` has.
7. **The alert feed pages by offset.** Offsets can skip or repeat across pages when rows are
   inserted between them. Acceptable for a feed sorted newest-first where the churn is at the
   top and a reader is walking down; a keyset cursor would be better.
8. **Alerts are as prompt as the drain's schedule**, unless the inline hook is on.
9. **`python -m app.operations drain-alerts --loop` is a foreground process**, not a service.
   Packaging it for Windows or as a container entry point is not done.
10. **The webhook sink has not been exercised against a real endpoint.** Its classification and
    construction are unit-tested; no test makes an HTTP request.
11. **The risk report's `place` filter is a prefix match on the resource key.** A server-level
    filter works by virtue of share and resource keys sharing a prefix, which is true today and
    is not a stated contract.

## 8. Security and privilege assumptions

* **Unchanged for collectors.** No collector file was touched and no new permission is required.
* **The product is still read-only about the estate.** Nothing here writes to a collected table
  or proposes a change to Windows. The only writes an operator makes are watches, which are
  ADG's own configuration.
* **Two new capabilities**, and the split is a control: `alerts:read` is the same disclosure
  class as the change feed a viewer already holds; `alerts:manage` is admin-only because
  somebody who could silently disable a watch could make an exposure land in nobody's inbox.
  Like ADR-0029's, this is a control against accident and casual misuse and not against a
  determined operator — anyone with the database credentials can do anything.
* **An alert payload is a disclosure.** It names SIDs, account names, UNC paths and what
  changed, and **it leaves the building**: a webhook sink posts it to whatever URL the policy
  names. That is a larger exposure than any other feature in ADG has, and the two controls on it
  are that the URL is operator configuration and that `alerts:manage` is admin-only.
* **The alert policy file may carry a credential**, so it is configuration and never source
  control. `.env.example` says so and ships no example token. The webhook sink sends
  `Authorization: Bearer <token>` only when one is configured.
* **The webhook sink does not follow redirects.** A 3xx is classified permanent, because
  following one would deliver an estate's exposure report to a host nobody configured.
* **Error text from a receiver is truncated to 500 characters** before it is stored, so a
  receiver's HTML error page does not end up in ADG's database.
* **The browser's write surface is two declared route handlers.** The generic proxy still
  forwards GET only, so widening it did not become a route into ingestion.
* **A rejected request never reaches the database.** Both new routers declare their capability
  at the route, which `tests/api/test_authorization.py` proves with a database that raises if a
  session is opened.

## 9. Migration and compatibility notes

* **`0013_alert_pipeline` is additive.** Four tables, thirteen indexes. No existing column,
  index or constraint changes.
* **`0014_merge_alerts_and_reviews` creates and drops nothing.** It joins this phase's branch
  to the other session's `0013_access_review_workflow`, both of which grew off
  `0012_merge_concurrent_phases`. Without it `alembic upgrade head` refuses with *"Multiple head
  revisions are present"*. Verified: a database created empty and brought to `head` applies
  every revision in order and contains all four alert tables with the declared columns, indexes
  and constraints.
* **There is no backfill, deliberately.** There are no alerts before this revision because
  nothing was watching. Manufacturing them from current state would date every one to the
  migration and claim somebody had been told.
* **`downgrade()` drops the four tables.** What is lost is not recoverable by re-running
  anything: which alerts were delivered, to whom, and when. Re-running detection over today's
  facts produces today's alerts dated today, with no evidence of what was announced in March.
  Watches are lost too, which is configuration somebody has to enter again.
* **The OpenAPI snapshot was regenerated**, which necessarily includes the concurrent session's
  routes. That is correct and it fixed two pre-existing hermetic failures. Regenerate with
  `python -m app.contracts.openapi` after any further route change.
* **A client reading `SubjectView` from the published document must now read
  `FindingSubjectView` for a finding's subject.** Nothing shipped against the colliding name —
  it existed only between this phase's first generation and the rename.
* **No collector contract change.** Version stays `1.3`.
