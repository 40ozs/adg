# ADR-0039: Demo is a deployment boundary drawn at ingestion, not a switch

- **Status:** Accepted
- **Date:** 2026-10-10
- **Phase:** ADG-DEMO-MODE-01
- **Deciders:** ADG maintainers

## Context

ADG needs to run as a demonstration, as an end-to-end test bed and eventually as a public
portfolio deployment, on a synthetic estate (Null Meridian) generated by a separate effort,
without Windows infrastructure. The obvious shapes — a separate demo app, a "demo data" toggle,
a demo-only schema, or demo objects fed straight to the UI — each either stop exercising ADG
itself or make a public instance one click away from being a connected one.

Two facts about ADG narrow the design. Its backend holds no directory, SMB or PowerShell
client (ADR-0004): collection is pushed by Windows collectors to `POST /api/v1/scan-runs`. And
everything ADG knows — history, current state, tombstones — is derived at ingestion
(ADR-0003, ADR-0018).

## Decision

1. `ADG_RUNTIME_MODE` (`production` | `demo`) is a validated `Settings` field read once at
   startup. Unknown or empty values are startup errors; only an unset variable means
   production. No route, header or UI control can change it.
2. The boundary is the ingestion API. In demo mode, synthetic collector-protocol transcripts
   are posted through the **same routes** by an in-process provider
   (`app.demo_mode.ingest`), using dependency overrides that exist only on an application
   object that never listens; the served application refuses those routes (`demo_only`).
3. Synthetic data is consumed through a contract (`app.demo_mode.datasets.SyntheticDataset`:
   metadata, generations, probes) from generators that own it. Demo Mode never generates data
   and never substitutes one dataset for another.
4. A demo database is identified three ways — runtime mode, a `demo` database name, and a
   `deployment_marker` row written only when the reset initializes an *empty* database — and
   nothing is wiped or served unless all hold.
5. Every mutating route is classified (supported / simulated / unavailable) in one exhaustive,
   tested table enforced by a backend dependency on every route.

## Alternatives considered

| Alternative | Why it was rejected |
| --- | --- |
| A separate `adg-demo` app or fork | Demonstrates a copy, which drifts; the point is to exercise ADG. |
| Seed rows directly into the tables | Bypasses validation, history and reconciliation — the parts most worth showing — and could produce states no collector can. |
| A runtime/UI toggle between demo and live | A public demo would be one request away from a connected one. |
| Demo-only schema | Would not exercise real persistence, current-state queries or migrations. |
| Database-name convention alone | A guard somebody edits; the marker cannot be satisfied by editing a URL. |
| Fall back to the reference estate when Null Meridian is absent | A silent substitution of what the deployment shows; refused with the dependency named instead. |

## Consequences

**Positive**

- Every synthetic observation exercises the real ingestion, history and current-state code;
  the demo is an integration test of the product.
- A demo deployment needs no Windows infrastructure and no production credential.
- Production behavior is unchanged: the guard is a no-op, the demo router is absent, and the
  only schema change is one empty table production never reads.

**Negative**

- An additive migration (`0017_deployment_marker`) and three additive response fields
  (`/version.runtime_mode`, `/health/ready.runtime_mode`, `.data_source`) and one public route
  (`/runtime`).
- The canonical dataset is a cross-branch dependency until the Null Meridian generator merges.
- A public demo still needs a visitor sign-in decision (development auth is refused with
  `ADG_ENVIRONMENT=production`).
